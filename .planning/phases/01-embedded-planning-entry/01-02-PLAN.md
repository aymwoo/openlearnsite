<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| teacher browser → `js/courseedit.js` panel state | User-entered planning fields and existing editor content are assembled client-side before submission |
| AI response → course editor result surface | Provider-returned text crosses into the browser UI and could become an XSS sink if rendered unsafely |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-05 | I | result panel in `js/courseedit.js` | mitigate | Render successful AI output with `textContent`/`innerText` and keep raw HTML insertion out of the result container |
| T-01-06 | T | request payload assembly | mitigate | Send only structured fields (`topic`, `grade`, `duration`, `teachingGoals`, `existingCourseContent`) plus `action=activityPlan`; do not expose an editable final prompt field |
| T-01-07 | D | course editor UX | mitigate | Preserve existing editor switching and save hooks, and keep request button disable/re-enable behavior so repeated clicks do not flood the handler |
| T-01-08 | R | regression-sensitive page wiring | accept | Use repository regression tests instead of adding runtime telemetry in this phase; the risk is low and bounded to teacher authoring UI |
</threat_model>
